AI CODING AGENTS · A FIELD GUIDE

Multiply your productivity in a nutshell

Used right, an agent doesn’t add to your output. It multiplies it.

Presented by P.M.C

Picture two swordsmen. One fights with a single sword in his hand: that is you, working alone. The other is a sword immortal who controls ten flying swords at once: that is you with agents, used right. Same person, ten blades. The rest of this talk is about how to become the second one: seven mental models, then the system we actually use.

PART 1

Mental model

Seven habits that turn an agent into a multiplier

Seven habits, one slide each. The last two, shape first and verify, are highlighted because they matter most: an agent that shares your picture of the outcome, and can check its own work, is the one you can trust with more.

01 · DELEGATE

Trust the agent with the work

Your job moves from typing to deciding.

MENTAL MODEL · 01 / 07

A real example. Checkout starts returning 500s. The old reflex: open the Cloud Console, go to Logs Explorer, and scroll, filter and squint at log lines by eye, jumping between services and time ranges. The new reflex: tell the agent what is broken and let it read the logs itself with the gcloud CLI. It filters the errors, spots that they all say the connection pool is exhausted, links that to the last deploy, finds the pool size in config, and hands you a fix with a failing test. Same incident, a few minutes instead of most of an hour, and your job moves from reading logs to deciding on the fix. Whenever you start something, ask first how the agent can do it.

02 · CONTEXT ENGINEERING

Keep the agent in the smart zone

Aim for 300–400k tokens of context at most, per task.

One task, one session

Start fresh for each task instead of piling work into one chat.

Hand off a summary

Carry a short brief or plan file forward, not the whole transcript.

Load only what matters

Point at the files the task touches; let subagents read the rest.

MENTAL MODEL · 02 / 07

Agents get worse as context fills up: they forget early instructions and repeat mistakes. Treat context as a budget. Keep each task to roughly 300 to 400 thousand tokens. When you approach that, compact, or write a short handoff and start a fresh session. Subagents are a context tool too: they read widely and return only the conclusion.

03 · GIT WORKTREES

One repo, many agents, no collisions

git worktree add ../app-auth -b feat/auth

Each agent gets its own folder and branch, so parallel work never touches the same files.

MENTAL MODEL · 03 / 07

A worktree is a second checkout of the same repository in its own folder, on its own branch. Give each agent a worktree and three tasks can run at once: a feature, a search change and a bug fix, each merged back when its tests pass. One rule: stop the dev servers a worktree started before you delete it.

04 · EFFORT

Low and medium effort for most work

Default. Scouting, small features, fixes, docs.

Only for a high blast radius. Migrations, auth and payments, big refactors.

MENTAL MODEL · 04 / 07

Higher effort is slower and costs more, and on ordinary work it often overthinks. Low and medium handle most tasks well. Reach for high, xhigh or max when a mistake is expensive: a data migration, authentication or payments, a large refactor, or an architecture call.

05 · RIGHT MODEL

The right model for each job

Match the model to the job, not to your habit.

MENTAL MODEL · 05 / 07

Not every step deserves the biggest model. Scouting and reading code is many small calls, so use a fast, cheap model like Haiku or GPT luna. Thinking and planning is where Opus or the GPT sol class earns its cost. Save the strongest model for the hardest calls. Commits and pushes are mechanical: give them a fast model. Subagents make this easy, because each one can be pinned to its own model.

06 · SHAPE FIRST

Shape it first, in one shared language

1

Interview before building

Let the agent ask questions until you both see the same outcome.

2

Write the words down

One glossary of domain terms for you, the agent and the team: DDD’s ubiquitous language.

3

Then build

Plans, code and tests use the same names.

MENTAL MODEL · 06 / 07

Most bad agent output is misalignment, not bad code. Before any work starts, let the agent interview you until you share the same picture of the outcome. Then write the domain words down once, in a glossary, so you, the agent and the rest of the team all say the same thing. That is Domain-Driven Design’s ubiquitous language, and it also makes the agent far less wordy.

07 · VERIFY

Build a system the agent can verify

Tools

Shell, browser, test runners.

Skills

Repeatable workflows it loads.

Hooks

Fire on every step, no prompt needed.

Guardrails

Block secrets and risky commands.

Connectors

MCP links to GitHub, docs, data.

Verify

Tests, types, browser checks, logs.

If the agent can’t check its own work, you become the test suite.

MENTAL MODEL · 07 / 07

This is the most important slide. A proper system has six parts: tools to act, skills for repeatable workflows, hooks that run on every step, guardrails that block secrets and risky commands, and connectors over MCP to GitHub, docs and data. Above all, give it a way to prove its work: tests it can run, types it can check, a browser it can drive, logs it can read. An agent in an act, check, fix loop finishes work. An agent without one hands you work to check.

PART 2

The system in real life

What we actually run, from the harness up

Part two is concrete, in two layers. First the harness. Then the skills on top of it, where we look at two options side by side: Matt Pocock’s popular open skill set, and our own AI Factory skills, which cover the whole development cycle.

SYSTEM · 01

Pick your harness first

THE SYSTEM IN REAL LIFE

The harness decides what everything else can do, so choose it first. Either go for the most intelligent model and accept the cost, or go for a harness that reaches many models and route each job to the cheapest one that can do it. Skills, agents, rules, hooks and connectors all plug into whichever you pick.

SYSTEM · 02 · SKILLS FOR REAL ENGINEERS

mattpocock/skills

Small, composable skills straight from Matt Pocock’s own .agents folder. They work with any model.

Matt Pocock’s skills are the best-known public skill set right now: over 300 thousand stars and 25 thousand forks on GitHub as of today. Each one targets a failure mode: grill-me fixes misalignment, a shared glossary fixes verbosity, tdd and diagnosing-bugs fix code that doesn’t work, and improve-codebase-architecture fights the ball of mud.

AI FACTORY · END TO END

One line from idea to release

/aif-brainstorm → /aif-plan → /aif-serve → /aif-code-review → /aif-ship

THE SYSTEM IN REAL LIFE

Work moves down one line. Shape the idea with advise, brainstorm or research. Plan it into phases, each with a Tests First section. Serve writes the failing tests first, then the code that turns them green, then refactors. Review checks the change against evidence, and anything it finds goes through debug and fix, with a failing test first, before it goes back to review. Ship takes the branch through PR, merge and release. Everything the skills write lands in the .aif folder.

AI FACTORY · WHEN YOU’RE UNSURE

Not sure yet? Advise or brainstorm

THE SYSTEM IN REAL LIFE

Don’t plan what you can’t describe. If you don’t yet know what outcome you want, run advise: it interviews you one question at a time and gives honest advice, including what not to do. If you know the outcome but not the approach, run brainstorm: it compares options and ends with an accepted outcome. Once both are clear, plan.

AI FACTORY · CHEF MODE

A senior chef on the catwalk

/aif-serve .aif/plans/rate-limit --chef

Advises only. Never writes code or overrides a gate.

Strongest model. Fable on Claude Code, gpt-6-astra on Codex.

THE SYSTEM IN REAL LIFE

Chef mode puts aif-chef, running on the strongest model, over the workflow. It steps in after each phase, when work is stuck, before a risky step and once a PR’s checks are green. It only advises; the main agent stays responsible. The flag carries down the chain: brainstorm, plan, serve, fix, test, code-review and ship all support it. And plan with --chef writes a handover plan that a smaller model can follow.

AI FACTORY · PRO-MAX MODE

Five cooks, one judge

/aif-plan add rate limiting --pro-max

Winner

Plan, debug, test and more keep the best answer, never a blend.

Union

Code review and recon keep every finding that checks out.

Fails closed

Under five usable candidates: nothing is written.

THE SYSTEM IN REAL LIFE

Pro-max trades cost for quality. The skill builds one evidence packet and one scoring rubric, sends them to five independent candidates in parallel, and aif-chef on the strongest model scores them. Most skills keep the single best candidate unchanged, because a blend is not what the judge checked. Code review and recon keep the union of findings that check out, so a catch made by one candidate isn’t lost. If fewer than five candidates are usable, it writes nothing. Each run leaves a one-line receipt naming the pick.

AI FACTORY · RED-TEAM MODE

Attack the plan before the code exists

/aif-plan red-team .aif/plans/rate-limit

Security first

Auth bypass, injection, data exposure, privilege escalation, OWASP Top 10.

Evidence or it’s out

A finding without a file:line citation is rejected.

You decide, the plan heals

Accepted fixes go into the phases, then a whole-plan sweep.

THE SYSTEM IN REAL LIFE

Red-team mode attacks a plan before any code is written, when a hole is cheapest to fix. aif-plan sends hostile reviewers at it in parallel, two to four depending on plan size. The security adversary always goes first, looking for auth bypass, injection, data exposure, privilege escalation and the OWASP Top 10. A failure-mode analyst, an assumption destroyer and a scope critic join on bigger plans. Every finding must cite file and line from the real codebase, or it is rejected automatically. You decide which findings to accept, they are written into the phase files, and a whole-plan sweep removes any stale claims before serve is allowed to start.
